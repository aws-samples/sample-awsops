---
name: awsops-architecture-diagram
description: Draw or review evidence-backed AWS architecture diagrams (아키텍처 구성도) for AWSops diagnoses. Use for an editable Draw.io map, native PowerPoint diagram, or a diagram in the saved diagnosis briefing, including current-state and proposed designs.
---

Start with the decision the diagram should help the workload owner make. Use a supplied diagnosis, diagram or approved design and its assessment date. A reference deck can illustrate the overview, enlarged detail and decision caption. Build the new map from the customer's own evidence.

**Read the relationships before arranging the icons.** For each relationship to draw, identify the two endpoint identities, account or report scope, region or Kubernetes cluster, relationship type, source and relevant window. For a Pod, keep its UID when available. For traces, keep the trace node ID as well as its display name. Give a resource with several confirmed relationships a single node in the same view when its identity and scope match. Time-bound IPs, equal names and shared security groups need independent evidence before joining different observations. Multiple projections of one span count as one observation.

| What the source establishes | What to draw |
| --- | --- |
| Explicit membership, such as a resource in a VPC or a workload in a namespace | Enclose the member in the verified parent. A subnet's AZ, a route table's subnet association and a Pod's service membership each need their own evidence. Keep an unplaced peer in the enclosing region or in a labeled group of peers whose placement is unknown. |
| Configuration or permission, such as ALB-to-subnet attachment, SG use, a permitted route or a service selector match | Use a labeled line without arrowheads. State the relationship, for example “attached subnet” or “permitted path.” A selector describes eligibility; an EndpointSlice target reference can identify the actual Kubernetes endpoint. |
| DNS resolution or a network observation such as NFM contributors, flow logs or eBPF transport flows | Show the typed association with its source/window. Label a DNS-window correlation as inferred. A packet direction may inform a network-specific view; the application-call arrow requires caller/callee evidence. |
| An admitted caller/callee pair from X-Ray, OTel or an eBPF application trace | Draw an arrow from the recorded caller to the recorded callee. Keep unresolved workload binding visible next to the affected sample. Each additional hop needs its own pair; a statement about one end-to-end request requires a shared request trace. |
| Inventory only or contradictory identity | Show the confirmed components, scope and relevant action. Leave the endpoints separate until the conflict is resolved. |
| Requested target architecture | Give it a separate view labeled **Proposed**. Draw intended flows as design choices and identify the change, prerequisite and acceptance check. |

**Compose for the reader.** Put the main decision in the title or the caption. Use region, VPC, AZ, subnet and Kubernetes boundaries only where supported. A background panel can group observations by evidence source if it is visibly labeled as such. Use official AWS icons for identified services and plain labeled nodes for logical telemetry. A trace source such as X-Ray belongs in the caption unless it is itself an endpoint. Write the resource role first and the distinguishing ID second. A reference layout that mirrors AZs or inserts a standard ingress chain is suitable only when those elements exist in the source. Use an overview and a focused second view when putting placement and calls on one canvas would suggest an unverified path.

**Choose the native deliverable.** For editable Draw.io and a PNG preview, use the installed `aws-content-plugin:architecture-diagram` tools when available. For irregular application graphs, use explicit nodes/edges and neutral line ends for associations. For a separate editable PowerPoint, put the resource role and ID inside the native shape that anchors the connector. Moving that shape should move its label and the line endpoint together. An AWS icon can be embedded in the node fill. Draw.io and PowerPoint should agree on parentage, edge direction, qualifiers and the decision. The existing AWSops browser export reads Markdown tables; use the [saved-report contract](references/saved-report.md) for that path.

Verify the final render at slide size. Compare every container membership and line with its source, including both ends, arrowhead and time scope. Open the editable file to check connectors still point to the right shapes. Someone seeing only the figure should be able to say what is established, which decision it informs, and what check would change that decision.
